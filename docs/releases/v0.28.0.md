# chimera-memory v0.28.0 — Local Operational Memory & Work Packets

- **Source:** https://github.com/maclit64-lang/chimera-memory
- **PyPI:** not yet published — this note describes a candidate prepared locally;
  it is not a live release.

This is a **local release candidate**. It supersets the frozen v0.27.0 line and
bumps `chimera-memory` and `chimera-memory-types` together (lockstep) from
0.27.0 to 0.28.0. No evidence-settlement scoring semantics changed; the new
surfaces are additive, local, and advisory.

## Classification

Minor release.

## Theme

Where earlier releases recorded *what happened* (evidence) and *what settled*
(claims), v0.28.0 adds **local operational memory** — how agents worked — and
ways to package and review it. Everything in this release is **local evidence
and operational memory**: advisory only, read-only on read paths, and write-gated
where it captures new data. None of it is a correctness, safety, approval, merge,
or production-readiness signal, and none of it is a form of verification.

## What's new

### Evidence event foundation and settled-claim projection

An additive, read-only `EvidenceEvent` projection folds the local ledger
(claims, outcomes, scores) into a normalized event stream, and a `SettledClaim`
projection folds those events by claim id into a per-claim view (latest status,
event count, and which records exist). Both are deterministic and add no new
heuristics; they are the shared substrate the newer surfaces read from.

### Handoff filters

`chimera-memory handoff` accepts exact-match filters (session / claim / status
for the claim view; task-kind / tool / workflow / tag for tool lessons) plus a
tool-note limit, surfaced as an advisory markdown or JSON summary for the next
agent. Read-only.

### Tool Notes v1

Tool Notes are **manual, local, advisory operational lessons** — reusable notes
about how a tool or workflow worked on a kind of task (agent skill memory).
`tool-notes add/list/suggest/show` record and recall them by exact match only;
they are never inferred, ranked, or executed. `handoff` and `preflight` can
surface matching notes, quiet by default.

### Tool Activity and review-before-save Candidate Lessons

`tool-activity add/list` records local tool/workflow activity append-only.
`tool-notes candidates` projects **review-before-save candidate lessons** from
that activity: one candidate per activity with the required fields, with the
candidate lesson taken from the activity summary verbatim — never inferred,
ranked, or fuzzy/semantic matched. Saving a candidate is always a manual
`tool-notes add`; nothing is saved automatically. Candidates can be filtered
(`--task-kind/--tool/--workflow/--tag`, with `--limit`) and looked up by exact id
(`tool-notes candidates show <id>`), and surface quietly in `handoff`/`preflight`
only when a candidate filter is supplied.

### Work Packets

`chimera-memory work-packet` composes the handoff view and candidate lessons into
one portable **advisory review artifact** (Markdown or JSON): claims and their
settle/contradict/unresolved state, next inspection targets, the tool lessons that
apply, the candidate lessons available to review, and the applied filters. It
reuses the existing projections (no duplicated logic) and writes nothing to the
store; `--output` writes only an explicitly named file.

### Work Packet bundles and diff

`work-packet bundle --output-dir DIR` writes a portable four-file bundle
(`WORK_PACKET.md`, `work-packet.json`, `manifest.json`, `README.md`) whose
manifest records a sha256 and byte count for each content file.
`work-packet inspect DIR` verifies those hashes and byte counts.
`work-packet diff OLD NEW` is a deterministic **local packet comparison** of two
bundles or two `work-packet.json` files (summary deltas; claims added/removed/
status-changed; tool notes and candidate lessons added/removed). Bundle export
refuses a non-empty directory without `--force`; inspect and diff are read-only.

### Work Packet review threads

`work-packet thread add/list/inspect/diff-latest/diff` collect packet bundles
over time into a **local review thread index** under a thread directory, with an
append-only `index.json`, a human `INDEX.md` timeline, and per-snapshot bundles
(`wp_<UTC-stamp>_<8-char content hash>`). `inspect` verifies every snapshot's
hashes; `diff-latest`/`diff` reuse the packet diff. Thread `add` writes only
under the thread directory (never the local `.chimera-memory/` store); list /
inspect / diff are read-only.

### MCP surfaces (read by default, write-gated capture)

The local MCP server exposes read-only tools without extra flags
(`chimera_tool_notes_suggest`, `chimera_tool_note_show`,
`chimera_tool_note_candidates`, `chimera_tool_note_candidate_show`,
`chimera_work_packet`, and read-only review-thread tools `…_thread_list`,
`…_thread_inspect`, `…_thread_diff_latest`). **Write-gated capture**
(`chimera_tool_note_add`, `chimera_tool_activity_add`) is hidden and rejected
unless `chimera-memory mcp serve --allow-write` is set, exactly like the existing
write/execute gating. Read tools never create or mutate a store. Bundle/thread
*writing* stays CLI-only.

## Honesty boundary

Chimera Memory records local evidence and operational memory. Tool Notes,
Candidate Lessons, Work Packets, and review threads are **advisory** — they help
an agent or reviewer remember and inspect local work. They are not a correctness,
safety, approval, merge, or production-readiness signal, and not a form of
verification.

## Migration and compatibility

- Additive only. Existing ledger files, claims, outcomes, scores, and the X-Ray /
  `PR_EVIDENCE.md` JSON contract are unchanged.
- New local artifacts live in their own files: tool notes in
  `.chimera-memory/tool_notes.jsonl`, activity in
  `.chimera-memory/tool_activity.jsonl`; work-packet bundles and review threads
  are written only to directories you name explicitly.
- New CLI commands (`tool-notes`, `tool-activity`, `work-packet` and its
  `bundle`/`inspect`/`diff`/`thread` subcommands) are additive; existing commands
  and their output shapes are preserved.
- `chimera-memory` and `chimera-memory-types` move together to 0.28.0; the
  inter-package dependency floor tracks the same line.

## What did not change / non-goals

- No correctness, safety, or production-readiness certification.
- No automatic saving of candidate lessons; saving is always a manual step.
- No tool-use detection, log inference, ranking, scoring, routing, fuzzy/semantic
  or model-based matching, agent spawning, or workflow launching.
- No cloud account, hosted service, cross-repo memory, embeddings, or prediction.
- No merge of the `court/crt-foundation` history.
